# 核实

判定之前，先查清注释说的事现在是否成立、当初为什么写。

## 现在的行为

- 找调用方：`rg -n '<符号>'`。
- 找相关测试：`rg -n '<符号>' tests/`，并运行这些测试，比如 `uv run pytest tests/test_x.py -k <名字>`。
- 注释提到的依赖方、配置项、外部接口、文件，确认现在还存在：`rg -n`、读配置文件、查依赖声明（`pyproject.toml`、lock 文件）。
- 注释里写的数值、单位、顺序、取值范围，拿代码对一遍。对不上的，判 DELETE（内容已经和代码对不上）。

## 历史

运行本 skill 目录下的 `scripts/evidence.sh <文件> <起始行> <结束行>`，范围取注释和它说明的那段代码。它依次输出：

1. 这几行的 blame，按提交归并；
2. 这几行的修改历史，最多 20 条；
3. 提交信息里出现的 PR 编号；
4. `gh` 可用并已登录时，每个 PR 的标题和描述。

读这些提交信息和 PR 描述，找写注释时的外部原因。

## 实验

最强的证据是实验：删掉 workaround，或者违反注释说的约束，然后跑测试。实验在临时 worktree 里做，不碰工作区：

```sh
exp="$(mktemp -d)/exp"
git worktree add --detach "$exp" HEAD
cd "$exp"
```

改代码、跑测试，结束后回到原仓库运行 `git worktree remove --force "$exp"`。

- 测试失败：说明它确实必要，记下失败的测试名和报错。
- 测试通过，但仍有理由怀疑它必要：说明缺测试，在证据里写明「缺测试」，建议先补一个测试。

## 什么算证据

- 上游 issue、规格书、硬件手册、外部 API 文档的链接，或者仓库里收录的规格文档；
- 写明了外部原因的 commit message 或 PR 描述；
- 去掉之后会失败的测试。

## 什么不算证据

- 注释自己的说法；
- 「以前就这样」「一直这么写」；
- 没有说明原因的提交信息，比如 `fix`、`update`。

记录不足时，在证据一栏明确写「记录不足」，判定按 DELETE 处理。
