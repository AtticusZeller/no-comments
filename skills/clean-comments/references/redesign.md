# WORKAROUND 的处理

## 1. 锁定行为

先写一个测试，把现有行为，或者 hack 所防止的那个问题，固定下来。测试名说明它锁住了什么，比如 `test_load_accepts_bank_export_with_bom`。

确认这个测试在现有代码上通过；临时去掉 hack 时失败。去掉 hack 后测试仍然通过，说明测试没锁住问题，重写测试。

## 2. 定位根因

从症状出发，用 `investigate.md` 里的命令（`rg`、`scripts/evidence.sh`、实验），沿调用链往上游找，找到第一个不变量被破坏的位置。写下：

- 症状：hack 不在时会出什么错，哪个测试失败；
- 根因：哪个文件哪一行，哪个不变量被破坏；
- 证据：命令、输出、提交或 PR 链接。

## 3. 判断范围

「范围内修复」要同时满足：

1. 改动的文件都在本次清理范围内；
2. 不改公共接口；
3. 不新增依赖；
4. 原有测试和新写的锁定测试全部通过。

有一条不满足，就不改代码，写草图。

用户在场时，范围内修复也要先给出方案，用户批准后再动手。无人值守时只写测试和草图，不改代码。

## 4. 草图模板

```markdown
### <一句话问题>

**问题**：<hack 在哪几行，掩盖了什么症状>

**根因与证据**：<文件:行号，哪个不变量被破坏；命令输出、提交、PR 链接>

**建议的形态**：<改完之后代码应该是什么样，几句话或伪代码>

**影响面**：<要改的文件、公共接口、调用方>

**风险与验证方式**：<可能破坏什么，用哪些测试或步骤验证>
```

草图写完就停，不实现。`gh` 可用并且仓库在 GitHub 上时，把草图开成 issue，把链接写进报告；否则把草图原文放进报告。
